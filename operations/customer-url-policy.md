# SHO WEB SUPPORT — お客様の公開URL保護手順

更新日: 2026-11-05

## 原則
- 名刺・チラシ・看板・QRコードに印刷されるURLは、ホスティング会社の変更に左右されないものにする。
- GitHub Pagesの `github.io`、Cloudflareの `pages.dev` 等を **お客様の正式納品URLにしない**。
- 顧客本人が所有する独自ドメイン、またはSHOが登録・継続管理する自社ドメインの専用サブドメインを使用する。
- SHO管理の専用サブドメインは、自社ドメインの登録・自動更新・継続管理体制ができるまでは発行しない。
- 現在、自社ドメインは未取得。実在しないドメイン名を販売ページや契約書で案内しない。
- 公開サイトと管理システムは別。管理用の `sho-support.github.io` URL変更はお客様の恒久的URL変更に直結させない。

## 新規納品時の確認
1. 見積り・入金前に、**実際に使う正式URL** とドメインの所有者、年間更新費、管理責任を明示し、同意を得る。
2. お客様所有ドメインの場合は所有者本人の承認、SHO管理ドメインの場合はSHO名義での取得・更新設定を確認する。
3. 各サイト個別のホスト名を用意する。同じホスト名を2件へ再利用しない。
4. GitHub Pagesを利用する場合、サイトの非公開制作中は `docs/` の準備中ページのみ公開する。未承認の本体HTMLは公開しない。
5. GitHub Pagesのカスタムドメインに、当該ホスト名を設定する。ドメイン側のDNSに正しいレコードを登録し、HTTPSの正常接続を確認する。
6. **GitHubはワイルドカードDNSを推奨していない**。複数のサブドメインには原則として個別レコードを使用する。
7. 管理画面の正式公開処理はGitHubのCNAME設定とHTTPSで表示できることを照合する。未設定・接続不可なら公開せず、作成済みの制作案を保持する。
8. 実際の公開内容をスマートフォン・PCで最終確認し、正式URLだけを納品書・QRコード等に使う。
9. 実サイトの公開確認、問い合わせ経路の確認、お客様の承認後に納品とする。

**注意:** GitHub Pagesをプライベートリポジトリから利用するには、利用プランが条件を満たす必要がある。条件を満たさない場合は無理に顧客の制作データを公開せず、別のホスティング先で独自ドメインを使用する。

## 公開後の保護
- 管理画面の「ドメイン変更」「Repo設定」「新規SITE IDの重複上書き」を禁止する。公開済み案件は移行手順による個別処理のみ。
- 顧客URLが変わる可能性がある変更は、顧客確認・既存URLの確保・切り戻し計画なしに実行しない。
- ドメインを所有する当事者は **更新忘れを防ぐ自動更新・支払手段・期限監視** を必ず維持する。
- SSL/HTTPS証明書の失効、DNS障害、元ドメイン解約はURLが同じでもサイト表示に影響するため定期点検する。

## ホスティング先を移行する際
1. 旧公開先を残したまま、新公開先に同じファイルを展開。
2. 新ホスト側で独自ドメインを事前登録し、TLSと表示内容の確認が可能な形にする。
3. DNSのTTLを調整し、公開先を新環境に変更。
4. ドメイン名・パス構成・リンク・QRコード・画像・HTTPS・問合せ動作を検証。
5. キャッシュやDNS伝播の期間を考慮して旧環境も維持し、異常時に切り戻す。
6. 本番切替が安定してから旧環境を停止。**お客様へ案内するURLは変更しない。**

- SHO管理の顧客サブドメインを正式発行する設定・証明書・移行テスト。
- 3プランの本番E2E試験。現時点では顧客サイトの公開を伴う試験は未実施。
